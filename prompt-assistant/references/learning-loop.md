# 持续改进

## 两种更新速度

明确偏好和项目事实按用户的新信息及时更新。个人方法先形成候选，再验证；基础 Skill 不随单次会话自我重写。数据是可变资产，公共方法由作者维护。

## 哪些信号可以学习

| 信号 | 记录动作 | 不能推导的结论 |
| --- | --- | --- |
| “这段不错，先用它” | 案例 `accepted` | 已在目标工具生成成功 |
| “我试过了，角色一致，效果满意” | 以 `user_report` 记为 `effective` | 助手亲眼检查过产物 |
| 可见产物通过具体检查 | 以 `observation` 记录检查与结果 | 其他模型与场景必然同样有效 |
| “以后这个账号都这样” | 对应项目的明确偏好 | 对所有项目的全局偏好 |
| 同类失败多次出现 | 关联案例，提出候选方法 | 问题必定来自提示词 |
| 自己分析觉得好 | 诊断意见或候选假设 | 用户已认可、方法已验证 |
| 没有回应 | 保持原状态 | 沉默代表满意 |

关联可见证据和条目 ID，不保存隐藏推理。理论来源、推测原因、实际观察和用户报告应明确区分。

## 将经验变成个人方法

先记录候选方法的适用情境、具体做法、机制假设、不适用条件与相关案例。`record` 创建的方法一律为 `candidate`。

第一版采用如下启用门槛，它是保守的工程规则，不是统计显著性标准：

1. 至少两个不同任务的实际有效案例；同一任务的两个版本只算一个任务。
2. 两个案例均有与方法有关的对照描述：原结果、改动后的结果、保持的条件及判定依据。来源可以是观察或具体用户报告，不能是自评分。
3. 工具、场景与项目符合候选方法的适用范围；没有未处理的反例。仅在某项目验证的经验不要扩成通用规则。

用 `validate` 保存证据并启用；有害对照会拒绝启用。若后续支持案例出现混合或失败结果，工具将相关已启用方法置为 `review`，暂不注入下次任务。修订方法后重新作为候选验证，或者用 `revoke` 停用。不得为了过门槛虚构第二次试验。

## 何时整理

明确反馈出现时当轮记录。开始相关新任务时读取经验。发现同类案例反复出现、记忆相互矛盾或用户要求整理时，读取 `review` 队列，处理候选偏好、候选方法与失败案例。

去重依据语义键和范围，不以相似文字随意合并事实；保留有价值的失败与反例。旧记录的新近程度只能作为相关性辅助，不能自动压过用户明确长期偏好。按任务读取少量相关条目，必要时再 `get` 原文，避免把整个库塞进上下文。

Skill 没有常驻进程。没有被宿主执行、没有结果回流时，不承诺后台学习或自动刷新知识。模型和工具升级后，涉及版本的经验应重新核验。

## 可撤回与可检查

每次修订保留版本和证据。用户可以查看某条记录的历史，恢复偏好或项目条目；恢复的方法回到候选状态，不能绕过验证。`forget` 删除选中条目、历史、反馈和通过关联标记产生的派生条目，先用 `impact` 看清范围。不删除外部原始图片或文件。

反馈捕捉与方法采用的技术机制可以自动化，经验原因的判定仍由模型和用户证据支持。不要把“已保存了规则”说成“已证明质量提高”。
