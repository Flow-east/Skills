# 少量协作示例

全部为合成情境，用来展示判断方式，不应预先导入用户个人数据库。

## 1. 保留观点，帮助表达

用户：“模型越来越强，大多数任务可以多轮聊出来，完整上下文比套模板更符合习惯。但文生图、视频还是经常要把一段提示词发到另一个地方。我想把这段话讲清楚。”

判断：保留“多轮协作有效 → 仍有单次跨工具交付场景 → 助手帮助整理”的论证，不能改成“普通人不会写结构化提示词，所以要学万能模板”。如果用户只是让你写口播，应直接完成口播，不为提到提示词而接管任务；只有要求制作给另一 AI 的指令时才触发本 Skill。

给另一个写作工具的 Prompt 可以是：

```text
把下面的观点整理成一段适合视频口播的中文，听起来像我在分享使用经验。保留这三个意思及其关系：现在模型更强了，很多好结果来自多轮沟通和逐步补齐上下文，不需要一开始就写出完整模板；但文生图、文生视频等场景，经常需要把一段完整提示词交给另一个工具；因此我做了一个提示词助手，帮大家在这些时候把想法表达完整。措辞自然，别替我增加“所有人都必须学习提示词工程”之类的观点。
```

可以解释一句：“这里先固定你要保留的论证关系，避免润色时把意思改了。”不必讲一遍通用理论。

## 2. 一次要求不升级为永久偏好

用户：“这次的封面别放字，做得松一点。”

行动：把无文字、较疏朗布局写进本任务；不保存成全局偏好。若用户后来补充“这个账号以后都不放字”，才记录项目范围的 `cover.text` 偏好。下次用户明确要求加标题时，以本次指令为准，不擅自改变长期默认。

## 3. ‘不错’不等于生成效果成功

用户：“这段可以，我拿去试试。”

行动：将对应案例标为 `accepted`，保留未试用状态，正常结束。无需强迫用户当场交反馈。

后来用户：“第二版我试了，人物没变，但镜头乱动。”

行动：定位第二版，记为 `mixed` 和 `user_report`，分别记录人物一致与镜头失败。检查实际提示词和工具能力，优先调整镜头要求；不要把整套方法推翻，也不要把用户没提供的视频说成已观看。需要时只补问决定镜头写法的目标工具或运动方向。

## 4. 3D 粗糙要先看粗糙在哪里

用户：“让 Agent 用 Blender 把这个模型做精致一点，我不会说专业术语。”

判断：原模型或截图是否可见？是轮廓、接缝、材质、灯光还是导入游戏后的显示问题？如果没有素材，说明需要给目标 Agent 附原工程/参考图，用可执行的检查流程替代捏造具体缺陷。

```text
请检查附带的 Blender 工程和效果参考，先指出当前观感粗糙的主要来源，并用我能理解的语言展示关键差异。这个模型将用于游戏，请结合实际导出目标，在造型轮廓、边缘处理、拓扑、材质和灯光中优先解决影响最大的部分。保留已经确认的比例与造型方向。每轮完成后，用一致视角和光照做前后对比，让我判断是否更接近参考；提出会明显增加性能成本或改变美术方向的方案时，先说明取舍。不要仅通过增加面数判断完成度。遇到我需要参与的选择，用具体视觉效果解释，并教我完成这次判断所需的最少知识。
```

界面参数、UE 导入目标、移动端性能预算若已知应补入；不知道时不能凭空给具体数值。解释可以停在“精细度也可能来自轮廓和材质，面数不是唯一因素”。这不是完整开发流程，也不默认替用户执行建模。

## 5. 迁移对话时携带上下文

用户：“把我们聊的包装成一段 Prompt，我要给另一个工具。”

行动：从本会话提取已确认目标、受众、关键决定、限制和待附材料。只需把决定执行的内容写进成稿，不转存所有废弃讨论，也不能出现目标工具无法理解的“按照上面第三版”。最后独立列出“需一起附：参考图 A、文案原稿”。

## 6. 没有数据时诚实开始

新用户：“帮我写一个短视频 Prompt，按我的习惯来。”

行动：检查记忆；无可用偏好时坦白尚未积累，利用当前信息出一个可改版本或问一个决定性的风格问题。不要套用作者的账号、工具偏好与真实案例。公共示例不属于这个用户的历史。
